## תיקון לטענה המקורית — אומת 23/08/2026

המסמך המקורי טען שאין בפרויקט קובץ חוקים בגיט, והורה לייצא מהקונסולה ולשמור
קובץ חדש בשם `database.rules.json`.

**בפועל קיים בשורש הפרויקט קובץ בשם `firebase-rules.json`, והוא נמצא בבקרת גרסאות.**
תוכנו הוא חוקי Realtime Database מלאים: `users`, `events`, `presetLists`, `admins`.

הטענה שנשארה נכונה — והיא החמורה יותר — היא שהקובץ **אינו מחובר לשום צינור פריסה**.
`firebase.json` מכיל היום רק:

```json
{
  "functions": {
    "source": "functions"
  }
}
```

אין בו סעיף `database`. לכן שום פקודת פריסה לא מעלה את הקובץ הזה, לעולם.

**המשמעות המדויקת:** במאגר יושב קובץ שנראה כמו מקור האמת של הרשאות המסד, בזמן
שההרשאות שרצות בפועל נערכות רק בקונסולה. **אף אחד לא יודע אם השניים זהים.**
זה גרוע מ"אין קובץ" — כי קובץ שקיים ואינו נאכף יוצר ביטחון שווא.

- **פרויקט ברירת המחדל ב-`.firebaserc` הוא `shishi-shitufimt`, והוא אותו פרויקט

  המקורי: פריסת חוקים לפרויקט הלא נכון היא תאונה שקטה לחלוטין.

  לא תוקן כאן — `.firebaserc` הוא קובץ יסוד ומחוץ להיקף הקמפיין הזה.

### 🛑 תוצאת ההשוואה מול הקונסולה — החוקים **אינם** זהים

הייצוא מהמסד החי בוצע ב-23/08/2026 (`firebase database:get "/.settings/rules"`,
פרויקט `shishi-shitufimt`), והושווה מול `firebase-rules.json`. **הם נבדלים בשלושה
מקומות, וכולם באותו כיוון: מה שרץ בפרודקשן מחמיר יותר ממה שכתוב בקובץ.**

1. **הגבלת הוספת פריטים** — בפרודקשן, הכתיבה לפריט בודד בתפריט מותרת רק למארגן
   האירוע, או למשתמש באירוע שהוגדר בו במפורש שמשתתפים רשאים להוסיף פריטים ורק
   כל עוד לא חרג ממכסת הפריטים שנקבעה לו, או למי שיצר את הפריט מלכתחילה.
   **בקובץ שבמאגר כתוב במקום זה שכל משתמש מזוהה רשאי לכתוב כל פריט.**
2. **מונה הפריטים למשתמש** — בפרודקשן קיים חוק ייעודי לצומת `userItemCounts`
   שמאפשר לכל אחד לעדכן רק את המונה של עצמו, ורק בצעד אחד למעלה או למטה.
   **בקובץ שבמאגר הצומת הזה אינו מופיע כלל.**
3. **אינדקס `creatorId` על `menuItems`** — קיים בפרודקשן, חסר בקובץ. זה הבדל
   ביצועים ולא אבטחה, אבל הוא מעיד על אותו דבר: הקובץ פשוט ישן יותר.

**המשמעות המעשית, וזו הנקודה החשובה במסמך כולו:** פריסת `firebase-rules.json`
כמו שהוא — כלומר בדיוק מה שהמסמך המקורי הורה לעשות — **הייתה מבטלת בפרודקשן את
הגבלת הוספת הפריטים ואת מונה המכסה, ומחזירה את המסד למצב פרוץ יותר ממה שהוא
היום.** זו בדיוק התאונה שהאזהרה בראש המסמך נועדה למנוע, והיא הייתה קורית.

**המסקנה לצינור:** מקור האמת לקומיט הראשון הוא **הייצוא מהמסד החי**, לא הקובץ
שבמאגר. הקובץ שבמאגר אינו "מקור האמת שלא נאכף" — הוא פשוט לא מעודכן.

**הוכרע 23/08/2026:** מקור האמת לקומיט הראשון הוא **הייצוא מהמסד החי**. הקובץ
שבמאגר נדרס בתוכן שרץ בפועל, כולל שתי ההגנות שקיימות היום רק בקונסולה — הגבלת
הוספת הפריטים ומכסת הפריטים למשתמש. כך הקומיט הראשון ניטרלי מבחינת התנהגות
במלוא מובן המילה, ושתי ההגנות נכנסות לבקרת גרסאות בפעם הראשונה.

## למה זה מסוכן

האפליקציה מחזיקה נתוני משתמשים אמיתיים — שמות, מספרי טלפון (בהצעות טרמפים), ושיוך
לאירועים. החוקים שמגנים על הנתונים האלה הם הדבר היחיד שעומד בין מסד הנתונים לבין
האינטרנט הפתוח. וכרגע:

1. **סקירה חסרת ערך.** אפשר לסקור את הקובץ, אבל אין ודאות שהוא מה שרץ.
2. **אין היסטוריה אמיתית.** שינוי שנעשה בקונסולה אינו מותיר עקבות בגיט.
3. **אין גיבוי אמין.** שינוי שגוי בקונסולה — אין ודאות שהקובץ הוא מה שצריך לשחזר.
4. **אין תיעוד של הכוונה.** בעוד שנה אף אחד לא יזכור למה חוק מסוים נכתב כך.

זה בדיוק סוג הסיכון שלא מכאיב עד היום שהוא מכאיב מאוד.

## ⚠️ אזהרה קריטית לפני ביצוע

**אסור לכתוב את קובץ החוקים מאפס, ואסור להניח שהקובץ שבגיט הוא מה שרץ.**

חוקים שגויים ינתקו את כל המשתמשים מהאפליקציה באופן מיידי — או גרוע מכך, יפתחו את
המסד לקריאה וכתיבה של כל אחד.

תקדים בפרויקט: המיזוג של 23/08 הכיל `firestore.rules` עם התבנית הפתוחה לרווחה של
Firebase שגם פג תוקפה. הוא הוסר לפני שהזיק, אבל זה ממחיש כמה קל להרוס כאן.

## מה לעשות

### שלב 1 — לייצא את החוקים שרצים בפועל

בקונסולה: **Realtime Database → Rules**, ולהעתיק את התוכן **בדיוק כמו שהוא**.
לשמור לקובץ זמני בלבד, לא לדרוס שום דבר בשלב הזה.

### שלב 2 — להשוות מול הקובץ שבגיט

זו הפעולה החשובה במסמך. להשוות את הייצוא מהקונסולה מול `firebase-rules.json`
שורה מול שורה.

**🛑 תנאי עצירה מוחלט:** אם השניים אינם זהים — **לעצור ולדווח לפני כל פעולה נוספת.**
הבדל לכל כיוון משנה את התוכנית לגמרי:

- אם הקונסולה **מתירנית יותר** מהקובץ — יש בפרודקשן חשיפה שאפילו לא מתועדת.
- אם הקונסולה **מחמירה יותר** מהקובץ — פריסת הקובץ כמו שהוא **תפתח את המסד**.
  זו בדיוק התאונה שכל המסמך הזה נועד למנוע.

### שלב 3 — לקבע את המצב הקיים תחת שם תקני

לתת לקובץ את השם המקובל ש-Firebase משתמש בו, ולוודא שנשאר עותק אחד בלבד — לא שניים.

**הוכרע 23/08/2026:** הקובץ יקרא `database.rules.json`, ו-`firebase-rules.json`
יימחק **באותו קומיט**. הנימוק: שני קבצים ששניהם נראים כמו מקור האמת הם בדיוק
הבלבול שיצר את התקלה מלכתחילה, ומי שיריץ בעתיד `firebase init` יקבל קובץ בשם
התקני ויתנגש עם הישן.

### שלב 4 — לחבר לפריסה

ב-`firebase.json`:

```json
{
  "functions": {
    "source": "functions"
  },
  "database": {
    "rules": "database.rules.json"
  }
}
```

### שלב 5 — פריסה שאינה משנה התנהגות

```bash
firebase deploy --only database
```

בנקודה הזו נפרסים בדיוק אותם חוקים שכבר רצים. **ההתנהגות לא משתנה בכלום** — וזו
בדיוק המטרה: להוכיח שהצינור עובד, בלי לערבב את זה עם שינוי תוכן.

> **משיכת הוראה, 23/08/2026:** המסמך הציג את פקודת הפריסה כצעד שמבוצע מאליו.
> **זה נמשך בזאת.** אין פריסה לפרודקשן בלי אישור מפורש ונקודתי, גם כשהפריסה
> "לא משנה כלום" — ובמיוחד אז, כי דווקא הביטחון הזה הוא מה שמרדים את הבדיקה.
> אם החוקים שנפרסים אינם בדיוק הייצוא מהמסד החי, הפריסה **כן** משנה התנהגות.
