# בדיקות חוקי מסד הנתונים

הבדיקות היחידות בפרויקט. הן בודקות את `database.rules.json` מול האמולטור של
Firebase, ואינן נוגעות בפרודקשן, בקוד המוצר או בבניית הפרונטאנד.

## דרישה מקדימה — JDK 21

האמולטור של Realtime Database רץ על Java, וכלי השורה של Firebase דורש
**JDK 21 ומעלה**. גרסאות ישנות יותר נדחות עם הודעה מפורשת.

לבדיקה מה מותקן:

```bash
java -version
```

**שים לב:** ב-23/08/2026 היה JDK 21 מותקן על המכונה תחת
`C:\Program Files\Microsoft\jdk-21.0.12.101-hotspot`, אבל **לא בנתיב ההרצה** —
`java` לא נמצא כפקודה, וגם JDK 11 ישן קיים במקביל. יש להוסיף את התיקייה לנתיב
לפני ההרצה:

```powershell
$env:PATH = "C:\Program Files\Microsoft\jdk-21.0.12.101-hotspotin;" + $env:PATH
```

## הרצה

```bash
firebase emulators:exec --only database --project demo-shishi "node --test --test-concurrency=1 test/rules/*.test.mjs"
```

הדגל `--test-concurrency=1` אינו קישוט: כל הבדיקות חולקות אמולטור אחד וקבוצת
חוקים אחת, והבדיקה האחרונה מחליפה את החוקים ומחזירה אותם. הרצה במקביל תיצור
מרוץ על המצב המשותף.

התבנית `*.test.mjs` נחוצה — מסירת שם התיקייה בלבד גורמת ל-Node לנסות לטעון
אותה כמודול ולהיכשל.

## תקלת סביבה שכבר נתקלנו בה — "Unable to establish loopback connection"

אם האמולטור נופל מיד עם `Database Emulator has exited with code: 1`, וב-
`database-debug.log` מופיע `failed to create a child event loop` ואחריו
`Unable to establish loopback connection` — זו אינה תקלה בבדיקות ולא בחוקים.

מכונת ה-Java אינה מצליחה ליצור את הצינור הפנימי שלה, כי חיבור לשקע מסוג
Unix בתיקיית הזמניות של המערכת נכשל. תעבורת TCP מקומית דווקא תקינה, ולכן זה
נראה מבלבל.

**הפתרון:** להפנות את מכונת ה-Java לתיקייה אחרת עבור השקעים האלה, לפני ההרצה:

```powershell
$env:JAVA_TOOL_OPTIONS = "-Djdk.net.unixdomain.tmpdir=C:\Temp\jsock"
```

יש לוודא שהתיקייה קיימת. אומת ב-23/08/2026: עם ההגדרה הזו האמולטור עולה
כרגיל, ובלעדיה הוא נופל בכל פעם.

הקידומת `demo-` בשם הפרויקט מבטיחה שהאמולטור עובד לגמרי מנותק, בלי לגעת בשום
פרויקט אמיתי.

## מה נבדק

התרחיש שמוגדר ב-[../../DOCS/PLANING/09-database-permissions.md](../../DOCS/PLANING/09-database-permissions.md):

- משתמש ב׳ אינו יכול למשוך את רשימת כל האירועים, ואינו יכול למשוך את
  האירועים של משתמש א׳.
- משתמש א׳ **כן** מקבל את האירועים של עצמו — זו השאילתה שמסך המארגן מריץ,
  והיא הדבר היחיד שעלול להישבר מהשינוי.
- משתמש ב׳ פותח אירוע בודד לפי מזהה, מצטרף, וקורא — זרימת ההזמנה דרך קישור.
- מבקר שאינו מחובר אינו רואה דבר, כולל את רשימת המנהלים.
- הרשימות המוכנות הישנות נגישות לבעליהן בלבד.
- **בדיקת נסיגה:** מחזירה את חוק הקריאה הישן ומוכיחה שהדליפה הייתה אמיתית.

**וצד הכתיבה, שנסגר ב-23/08/2026** — ראה
[../../DOCS/PLANING/14-events-write-cascade.md](../../DOCS/PLANING/14-events-write-cascade.md):

- משתמש ב׳ אינו יכול לערוך את פרטי האירוע של א׳, לערוך או למחוק פריט שיצר אדם
  אחר, למחוק את כל התפריט של אירוע זר, או למחוק את כל האירועים במערכת.
- משתמש ב׳ אינו יכול להוסיף פריט לאירוע שלא איפשר זאת, לחרוג ממכסת הפריטים,
  או להזיז את המונה של מישהו אחר.
- תפיסת פריט, שחרורו, וההגנה מפני שני תופסים בו-זמנית.
- הוספת טרמפ אינה נספרת במכסה, כפי שהמוצר מתנהג.
- יוצר פריט מוחק אותו יחד עם ההרשמות של אחרים אליו; אדם שאינו היוצר אינו יכול.
- הצטרפות לאירוע שאין בו עדיין פריטים.
- המארגן ממשיך לערוך, למחוק ולהגר את האירוע שלו.

## שתי בדיקות שדורשות תשומת לב

**`sanity`** — מוודאת שהאמולטור באמת טוען את קובץ החוקים שלנו. אם שם המרחב
שגוי, האמולטור מגיש חוקים פתוחים לרווחה וכל שאר הבדיקות היו עוברות מהסיבה
הלא נכונה.

**`two people going for the same item at once`** — שתי תפיסות של אותו פריט
נשלחות במקביל, ונדרש שבדיוק אחת תצליח. זו הבדיקה שמוכיחה שההגנה מפני מרוץ
שרדה את המעבר מטרנזקציה על האירוע כולו לכתיבה ממוקדת. מול החוקים הישנים היא
נכשלה עם **שני** זוכים.

## למה הבדיקות משתמשות בספריית הלקוח ולא ב-REST

ההרשאות נבדקות דרך ספריית Firebase שהאפליקציה עצמה משתמשת בה. הסיבה מהותית:
הספרייה אינה משדרת "שווה לערך הזה" בפרוטוקול, אלא טווח שגבולותיו זהים. בדיקה
שהייתה מדברת REST הייתה עוברת בזמן שמסך המארגן נשבר בפועל.

הזרעת הנתונים לפני הבדיקות כן נעשית דרך REST עם הרשאת בעלים, כדי לעקוף את
החוקים בשלב ההכנה. זה מכוון.
